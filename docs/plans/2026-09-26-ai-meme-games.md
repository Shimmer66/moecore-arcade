# 摸鱼局：AI 梗的抽象玩法方案

日期：2026-09-26  
状态：`steady` 已从字网分拣改为“承诺实验室”，并扩展为五关挑战、自由实验、预算与星级、本地进度及角色图反馈；本文件中的三卡解谜与其他角色玩法仍为候选，尚未经过真人趣味性验证。

最新执行范围：用户指出原型仍只是接东西，并要求继续主动整活的方向；现已实现摆放气球、磁铁、锅和蹦床，模拟救援、运行时剪绳与断电，详见[承诺实验室记录](../games/steady.md)。以下三卡解谜关卡作为后续设计参考。

## 1. 这次要做出的感觉

**让 AI 熟悉的话术、能力和 meme 变成世界规则，再让这些规则产生意想不到、但能解释清楚的后果。**

用户明确的创作要求是：“抽象就是让你意想不到又合情合理。”

例如，GPT 说“我给你兜底”，画面底部真的张开一张网。它确实接住了用户，但用户背着“本周 KPI”“下月房租”和“人情债”一起落下来，网开始下沉。玩家需要处理这些重担，才能让承诺兑现。

笑点需要经过四步：

1. 玩家认出一个熟悉的话术或特点。
2. 它以出乎意料的形式在世界中生效。
3. 效果遵守明确规则，也带来可以预见的副作用。
4. 玩家利用规则解决问题，做出自己的结果。

“接住人”的物理操作可以保留，但题材要扩展到接锅、接需求、接住情绪、接住生活重担，以及接住自己刚刚说出口的承诺。各关卡要围绕统一操作组织，避免每个梗都增加一套按钮。

## 2. 项目定位与首轮范围

对外表达建议：**摸鱼局——把 AI 的话当真，会发生什么？**

定位：短局、可操作、有因果关系的 AI 荒诞喜剧。既让熟悉 AI 的人认出出处，也让不了解模型的人从画面理解目标和笑点。

项目已有六款可玩原型、统一网页宿主及角色素材，详见 [README](../../README.md) 和 [路线图](../roadmap.md)。这些可以提供试玩入口与工程基础。

当前方向建议：

- 首先验证《稳稳接住你》的“语言改变物理”玩法。
- 第二候选为《豆包说这样穿》，验证穿搭指令产生的荒诞造型。
- DeepSeek、Gemini、Claude、Kimi、Grok 保留各自独立的机制方向。
- 首轮交付范围为一个可玩的核心样例及约 20 人的观察记录，先验证笑点、因果和操作。

本次交付仅为方案。角色优先级、关卡、数值与投入规模都是建议；用户尚未选择具体实施范围。

## 3. 第一候选：《稳稳接住你》

### 3.1 核心设定

GPT 的安慰话在这里具有字面上的物理效力。玩家帮助它把用户送到出口，同时承担这些话引发的连锁后果。

一句话目标：**把用户和必须保留的东西安全送出去，兑现这一局的承诺。**

人物只是场景中的一个对象。生活重担、甩来的锅、不断增加的需求、撑不住的底线，都可以成为看得见、推得动、能改变路线的东西。

### 3.2 操作与规则

采用一个屏幕的物理解谜。玩家点击选择对象，再使用少量话术卡；卡片效果在图标和短预览中说明，场景变化后立即出现结果。

首个样例只保留三种卡：

| 话术卡         | 一致的物理规则                                               | 用途与副作用                                     |
| -------------- | ------------------------------------------------------------ | ------------------------------------------------ |
| 我给你兜底     | 在指定区域下方展开有限承重的网，接住落入其中的一切           | 能救人，也会接住砸下来的重担和杂物               |
| 先把这件事放下 | 让选中的角色放开手中或背上的指定物体；物体仍存在并受重力影响 | 人变轻了，但放下的东西可能堵路、压网，也可能垫脚 |
| 换个角度看     | 将可旋转场景区域转动 90 度，重力保持向下                     | 原来的墙可以成为地面，松散物体也会一起下落       |

卡片可以在多个合法目标上使用。玩家先看到作用区域，再确认使用；限制来自关卡给予的卡片次数、对象关系和空间，不依赖随机触发失败。

首版提供撤销一步、重开与结算。以通过关卡为主要目标，暂不加入倒计时压迫。

### 3.3 三个关卡场景

#### 第一关：我最近压力有点大

开场：用户背着写有“本周 KPI”和“下月房租”的大箱子，站在裂开的地板上。GPT 表示会兜底。

玩家最直接的做法是铺网让用户走过去；但网的承重提示清楚显示，人加两只箱子会超载。

可以在安全位置先放下部分重担，再铺网过路；也可以利用放下的箱子垫出一条路线。玩家若把箱子放在错误的位置，它们会堵住出口，需要撤销或改变角度。

**反转：人被接住了，生活重担也一起被接住。**  
**因果：网对所有重量遵守同一规则。**  
**操作：决定放下哪个物体、放在哪里、什么时候展开网。**

#### 第二关：这锅不该你背

开场：办公室里有人把一口写着“上线事故”的锅推向用户。GPT 承诺帮助用户把锅放下。

锅从用户背上卸下后仍沿斜坡滚动，里面还装着需要交付的文件。玩家必须同时保护用户和文件。

可以把锅稳在网里，让它成为运送文件的容器；也可以转动场景改变滚动路线。锅本来是负担，也可能被玩家用作过关工具。

**反转：甩锅、背锅和接锅都变成了真实的搬运与滚动。**  
**因果：放下只改变持有关系，锅不会凭空消失。**  
**操作：利用坡度、容器和网安排运输。**

#### 第三关：换个角度，路就通了

开场：用户已接近出口，一堵“需求变更”墙挡住去路。

转动区域后，墙成为脚下的平台，出口也随场景移动；原来放在架子上的需求文件开始下落。玩家需要先整理松散物体，或保留一次兜底，才能顺利抵达出口。

最后可以出现这样的局面：用户踩着之前挡路的墙过关，GPT 在下面接住自己转下来的整堆需求。

**反转：换个角度确实解决了问题，也改变了整个局面。**  
**因果：旋转作用于整个选定区域。**  
**操作：安排整理、旋转和兜底的顺序。**

这三个场景是关卡草案。具体解法、可解性和多解空间需要在操作样例中验证。

### 3.4 为什么玩家还会继续玩

- 同一句话在不同物体关系中有不同用途。
- 初次成功以后，可以尝试少用一次卡、保住更多物品或做出更有趣的解法。
- 失败能解释，撤销后可以立刻试另一个顺序。
- 过关画面记录自己的布局，玩家可以分享“我最后是这样接住的”。
- 后续关卡通过组合已有规则增加变化，保持操作数量稳定。

第一轮应验证“场景变化能否带来探索欲”。如果玩家只愿意看一次演出，暂不扩大关卡生产。

### 3.5 最小样例

先只制作第一关，包含一个用户、GPT、一张网、两只负担箱、一个出口和三张话术卡。

必要反馈：

- 网的承重、受力和失稳清楚可见。
- 被放下的物体保留碰撞和位置。
- 旋转前可看见作用区域，旋转后没有隐蔽规则改变。
- 角色会对发生的事作出简短、原创的反应。
- 玩家可撤销、重开并查看本局结果。

样例通过真人验证之后，才制作后两关、完整角色演出、挑战链接和结果卡。

## 4. 第二候选：《豆包说这样穿》

### 4.1 把穿搭建议推进一步

豆包穿搭视频中的“卷裤脚”和一本正经的搭配建议，可以变成一个有统一变形规则的游戏。

一句话玩法：**照着建议修改衣服，再带着这个造型真的走到约会现场。**

这里的扩展是：衣服改变以后，角色的外形、通行空间和移动条件也会跟着改变。

| 原创建议               | 游戏里的字面效果                 | 合乎规则的后果                           |
| ---------------------- | -------------------------------- | ---------------------------------------- |
| 裤脚再卷一点，会更利落 | 布料逐层堆积成环                 | 小障碍可以踩过去，但过大的裤脚会卡在窄门 |
| 气场要打开             | 外套展开，形成宽大的轮廓         | 可以借风滑行，也更容易被风吹偏           |
| 把腰线提上去           | 腰带沿服饰模板上移，改变造型比例 | 下摆形状随之变化，影响跨台阶和通过低处   |
| 再加一层，更有层次     | 新衣服真实叠在外层               | 获得新的搭配效果，同时增加体积           |

这些是原创的夸张游戏设定，不是豆包原话或真实模型输出。

### 4.2 一局流程

1. 接到一个具体场景，如“雨天赴约”。
2. 从八件衣物里搭配，执行、调整或跳过三条建议。
3. 在一段短路线上检验造型：雨、水坑、风、窄门等。
4. 出现问题可以回去修改一次。
5. 抵达后展示出门前、听完建议后以及实际到场的对照。

关卡硬要求清楚展示，例如带伞、过门、到达。审美采用风格描述，玩家自由决定。表情和评论围绕服装与发生的事故展开。

### 4.3 第一个验证范围

一个身体模板、八件服饰、两个变形操作、一段短路。先验证“改造结果会影响后续行动”是否让人愿意试第二套搭配。

新角色豆包尚未登记，需要补充自创设计和资源记录。文字气泡与提示音即可完成首轮；完整语音不作为依赖。

## 5. 其他模型也采用同一个创作标准

下列均为原创玩法候选。产品特点提供起点，具体荒诞效果由我们设计。

| 角色     | 原始特点或 meme        | 意想不到的展开                                                                   | 玩家实际操作                               |
| -------- | ---------------------- | -------------------------------------------------------------------------------- | ------------------------------------------ |
| DeepSeek | 深度思考、大肥鱼、白饭 | 每次“想深一点”都向下挖出一层思路地道；找到答案后，还要设法从自己挖出的深坑回来   | 选择分叉、保留回路、控制继续深入的时机     |
| Gemini   | Nano Banana、编辑图片  | 把挡路的石头改成气球确实能移走它，但绑在石头上的桥也跟着被吊起来                 | 圈定编辑区域、选择变化、保留重要连接       |
| Claude   | 写代码、修复、回退     | 为了修好漏水把水源关掉，机器正常了，旁边鱼缸却开始缺水；需要同时满足多个明确目标 | 修改少量规则积木，观察关联影响，必要时回退 |
| Kimi     | 长文本理解、摘要       | 把一屋子的文件压缩成几块“重点”，桌面腾空了；过关所需的细节还得从原文里展开找回   | 选择压缩范围、保存索引、按需展开           |
| Grok     | 幽默与叛逆感的定位     | 吐槽化成能弹射的文字；一句反击打退对方，也可能反弹回来                           | 选择反击时机和角度，控制连锁弹射           |

GLM 保留在现有角色阵容中，本轮尚未查到足够鲜明且有来源支持的独立玩法依据。

角色之间可以客串和互相制造局面，例如 Gemini 把重担改成气球，GPT 的兜底网因此被反向提起来。跨角色组合留到各自规则已经被玩家理解之后。

## 6. 创意筛选标准

每个新梗都写成四句话：

- 玩家原先以为会发生什么？
- 实际发生了什么？
- 这个结果为什么符合已经建立的规则？
- 玩家能做什么改变结果？

如果第三句只能解释为“因为 AI 就是会胡来”，需要重新设计。若第四句只有“看完台词点击下一步”，需要补上有意义的操作。

角色也要有发挥本领的时刻：GPT 可以通过巧妙兜底救场，豆包的怪搭配偶尔真能解决障碍，DeepSeek 深挖可以找到捷径，Claude 可以一次改动修好连锁问题。玩家应当能喜欢这些角色。

创意评估表：

| 维度   | 判断问题                               |
| ------ | -------------------------------------- |
| 可识别 | 看过相关 AI 内容的人能否认出梗？       |
| 可理解 | 不懂梗的人能否从画面看懂发生的事？     |
| 有意外 | 熟悉表达是否产生了新的结果？           |
| 有因果 | 结果能否由明确规则解释？               |
| 能操作 | 玩家是否有至少一个会改变结果的选择？   |
| 可重玩 | 换个顺序、布局或组合是否值得再试？     |
| 好展示 | 一张图或十几秒录像能否呈现冲突和结果？ |

## 7. 验证与推广顺序

### 第一轮：观察约 20 人

约一半熟悉 AI 梗，一半不熟悉。只给链接和游戏内说明，记录：

- 能否独立完成第一次操作。
- 看到反转时是理解、发笑，还是困惑。
- 失败后能否说明原因。
- 是否主动撤销、重开或尝试另一种解法。
- 是否能用一句话把游戏介绍给朋友。
- 是否主动展示自己的结果。

“看着有趣”和“玩着有趣”分别记录。不要用亲友礼貌评价替代行为观察。

### 第二轮：100–300 人小范围试玩

仅对首轮出现主动探索、复玩或分享迹象的方向扩充内容。

分别记录页面到达、开局、完成、重开、分享动作和挑战链接带来的新开局。分享按钮点击、复制链接、实际转发和带来新玩家不是同一个指标。

第一批数据用于建立基线，不预设某个百分比能够证明爆款。连续两轮围绕同一问题调整却没有行为改善，就停止扩大该方向。

### 内容传播

从真实游玩中选取“承诺—字面实现—连锁后果—玩家救场”的短片。

例如：“GPT 真给我兜底了，连公司都兜住了。”只有游戏中确实存在相应场景时才使用这类文案。

每条内容只展示一个反转，链接直接进入对应关卡。结果卡包含实际局面和同关挑战入口，让朋友可以尝试自己的解法。

先在已有联系、允许试玩招募的圈层验证，再评估 B 站、抖音、小红书等内容渠道。当前是网页项目，发布前需要实测各平台的链接、扫码和打开流程。

本方案没有执行对外发帖、邀请、购买推广或部署。

| 单元              | 交付物                                 | 前置依赖                 | 完成条件                                   | 状态   |
| ----------------- | -------------------------------------- | ------------------------ | ------------------------------------------ | ------ |
| A. 语言物理样例   | 第一关、三张卡、撤销和重开             | 明确物体与卡片规则       | 至少一种正常解法可完成，所有变化有可见因果 | 待开始 |
| B. 首轮观察       | 约 20 人的行为与问题记录               | A 可玩、试玩者到位       | 能判断笑点、理解与操作的主要问题           | 待开始 |
| C. GPT 三关版本   | 两个新场景、角色反馈、结果卡、同关链接 | B 出现继续投入证据       | 三关正常流程与至少一种替代解法可验证       | 待开始 |
| D. 豆包操作样例   | 八件衣物、两种变形、一段检验路线       | 角色草图、图层和变形规则 | 玩家理解穿搭与过路结果的关系，并尝试调整   | 待开始 |
| E. 小范围公开试玩 | 通过发布检查的版本、真实素材、行为记录 | C 或 D 达到发布要求      | 获得可用于选择方向的真实结果               | 待开始 |

建议先给 A 设置约 3–5 个开发工作日的试验投入上限。这是控制原型规模的建议，不是工期承诺；试玩招募和新美术耗时另计。

现有架构可复用游戏宿主、动态加载、暂停、重开与结算。新玩法采用独立游戏包，遵循 [架构与包边界](../architecture/README.md)。物理库是否必要由 A 的表现决定，不预先建立通用引擎。

验证重点：

- 卡片目标、旋转区域、重量与碰撞遵守一致规则。
- 撤销还原完整局面，重开没有残留状态。
- 暂停和失焦停止物理与输入。
- 分享链接在同一规则版本下还原相同关卡。
- 穿搭变形、遮挡和碰撞保持一致。
- 在真实手机上检查点击目标、预览与操作反馈。

程序检查用于证明规则和流程正常；趣味性由真人观察补充。

## 9. 边界与后续决策

游戏由本地规则和原创台词驱动，首轮不需要真实模型请求。运行时生成内容会增加时延、成本和关卡不可控性，若以后确有玩法需求再独立评估。

沿用现有项目的角色与资源登记流程。研究引用的社区图片、原文与声音不自动成为可分发素材。豆包需要新增角色记录和自创素材，尚不具备现成完整资源。

首轮以观察和本地记录验证。若公开阶段需要跨用户统计，将最小匿名事件上报列为新增范围；不把已有本地存储当作已具备统计后端。

核心样例验证后再决定最终主打、投入预算、首发渠道和是否接入原生小游戏平台。这些后续选择不影响制作本地样例。
